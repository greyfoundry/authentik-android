# Forms and Sensitive Actions

## Pattern: Explicit forms and risk-aware confirmation

- Problem: Configure providers and other complex resources, validate fields, protect secrets, and confirm sensitive or destructive actions without losing state or disguising uncertain outcomes.
- Project constraints: The central action policy assigns `READ`, `WRITE`, `SENSITIVE_WRITE`, `DESTRUCTIVE`, or `CREDENTIAL`; no screen invents its own protection; secrets never enter logs, Room, clipboard history, or bug reports; administrative writes are online-only and non-idempotent mutations are not retried without tested semantics.
- Sources reviewed: [Compose state guidance](https://developer.android.com/develop/ui/compose/state), [Material 3](https://developer.android.com/develop/ui/compose/designsystems/material3), locked `andromeda/andromeda/src/commonMain/kotlin/design/andromedacompose/foundation/accessibility/AccessibilityDefaults.kt`, `andromeda/andromeda/src/commonMain/kotlin/design/andromedacompose/components/inputs/TextField.kt`, `compose-cookbook/app/src/main/java/com/guru/composecookbook/ui/learnwidgets/DialogExamples.kt`, and the Tier 3 access boundaries in `../sources.md`.
- Observed pattern: Long forms work best when labels remain visible, validation stays next to the field, advanced groups are disclosed progressively, and the final confirmation names both target and effect. Community component anatomy can reveal useful state coverage but is not an authority for current APIs.
- Adopt: Preserve non-secret draft state, distinguish required, optional, inherited, and secret values, validate known rules before dispatch, retain actionable server validation, explain the risk tier, require the central policy's authorization, and reconcile ambiguous network outcomes before offering another mutation.
- Reject: Placeholder-only labels, prefilled secret placeholders, generic confirmation copy, hidden destructive actions, optimistic success after an ambiguous timeout, automatic replay, custom component libraries, and gallery-derived copy or trade dress.
- Compose translation: Use Material 3 text fields, supporting text, sections, dialogs or dedicated confirmation surfaces according to complexity, saveable non-secret state, immutable ViewModel state, explicit callbacks, and a shared policy-owned authorization result. Keep secret values in the narrowest possible state holder.
- Accessibility checks: Persistent labels, error semantics associated with their fields, ordered focus, 48dp controls, clear required-state text, confirmation title that names the target, no color-only validation, keyboard and switch-access operation, and large-text layouts without clipped actions.
- Validation: Unit tests cover validation and action-policy decisions; Compose tests cover restoration, error association, progressive disclosure, confirmation wording, and disabled dispatch; transport tests cover success, validation failure, permission denial, pre-dispatch failure, ambiguous timeout, reconciliation, and unsupported capability.
